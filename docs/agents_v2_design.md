# تصميم agents_v2 — نظام وكلاء بطريقة Anthropic لخط مقالات SEO

> الحالة: وثيقة تصميم (الخطوة 3 من التفويض). المصطلح «يجب» يعني مفرَضاً بالكود،
> و«التفويض» هو رسالة المالك المؤسِّسة لهذا العمل. لا شيء هنا يُستدعى من أي مسار إنتاج.

## 1) الأهداف والقيود الثابتة

الهدف: رفع جودة توليد المقالات فوق «الخط المحسّن» الحالي بمعمارية وكلاء متعددة
(منسّق + باحثون + كاتب + ناقد + بوابات حتمية + ناشر كود) بأسلوب Claude Code:
أدوات بأقل صلاحية، مخططات I/O متحقَّق منها، بوابات حتمية حاكمة، وحدود صارمة بالكود.

القيود الثابتة (من التفويض):
- المفتاح عبر `secrets.CLEANAPIS` فقط داخل `env:` في GitHub Actions؛ لا طباعة ولا تخزين.
- لا استدعاء لأي كود agents_v2 من مسار إنتاج؛ الناشر يكتب artifact فقط.
- المحتوى المجلوب من الأدوات **بيانات لا تعليمات** (هجوم الحقن مُختبَر في model_fit).
- كل الأدوار تمر عبر `agents_v2/llm_provider.chat()` — لا HTTP مباشر من الوكلاء.

## 2) المعمارية

```
                ┌────────────────────────────────────────────┐
                │ ORCHESTRATOR (نموذج من فئة الأقوى)          │
                │ خطوات: خطة → تفويض → تحقق → قرار            │
                └──────┬─────────────────┬───────────────────┘
        تفويض بحث ×3   │                 │ تجميع مصادر للكاتب
        بالتوازي       ▼                 ▼
   ┌────────────┐ ┌────────────┐ ┌────────────┐   ┌──────────────────┐
   │ RESEARCH 1 │ │ RESEARCH 2 │ │ RESEARCH 3 │   │ WRITER (نموذج آخر)│
   │ web_search │ │ web_search │ │ web_search │──▶│ كتابة قسم فاشل    │
   │ fetch_page │ │ fetch_page │ │ fetch_page │   │ فقط، ≤2 محاولات   │
   └────────────┘ └────────────┘ └────────────┘   └────────┬─────────┘
                                                            ▼
                                     ┌────────────────────────────────┐
                                     │ GATES (حتمي — كود فقط، حاكم نهائي)│
                                     │ نسخة منطق #450 داخل agents_v2    │
                                     └────────┬───────────────────────┘
                                              ▼
                              ┌────────────────────────────┐
                              │ CRITIC (نموذج ≠ الكاتب — استشاري) │
                              └────────┬───────────────────┘
                                       ▼
                        ┌───────────────────────────────┐
                        │ PUBLISHER (كود فقط): artifact │
                        │ بلا commit ولا PR ولا نشر      │
                        └───────────────────────────────┘
```

ملاحظات التصميم:
- **المنسّق** لا يكتب محتوى؛ يخطط ويوزع ويقرر التوقف. مخرجاته JSON مُتحقَّق منه.
- **الباحثون الثلاثة** يعملون بالتوازي على جوانب مختلفة للموضوع (منافسون / زوايا تقنية
  / أسئلة مستخدمين). قراءة فقط: بحث + جلب صفحات من قائمة سماح.
- **الكاتب** يعيد توليد القسم الفاشل فقط (بوابة فاشلة محددة بالاسم) بحد محاولتين،
  لا يلمس الأقسام الناجحة.
- **الناقد** بنموذج مختلف عن الكاتب (`must_differ_from` مفرَض في llm_provider) —
  رأيه استشاري: ملاحظات تُمرر للكاتب، ولا يتجاوز حكم البوابات الحتمية أبداً.
- **البوابات** الحاكم النهائي: نسخة `gates.py` من فرع #450 (قراءة فقط) داخل
  `agents_v2/gates_local.py` — نفس النافذة 2550–3100، meta 120–160، faq8، جدول
  مقارنة، ToC، Verdict، ودرع تخريب الماركداون. لا حكم نموذجي في البوابات إطلاقاً.

## 3) الأدوات (أقل صلاحية)

| الأداة | متاح لـ | المدخلات (JSON Schema) | المخرجات | حدود |
|---|---|---|---|---|
| `web_search` | الباحثون فقط | `{query: string, n: int≤8}` | `{results: [{title, url, snippet}]}` | عبر SearXNG المحلي؛ 8 نتائج كحد |
| `fetch_page` | الباحثون فقط | `{url: string}` | `{url, title, text≤6000ch}` | نطاقات قائمة السماح فقط؛ مهلة 15s |
| `submit_section` | الكاتب فقط | `{section_h2, body_markdown}` | تأكيد | إخراج مُهيكل مُتحقَّق منه |
| `finish` | المنسّق فقط | `{decision: "proceed"|"stop", reason}` | — | نقطة توقف إلزامية |

قائمة سماح نطاقات الجلب (للتجربة): `en.wikipedia.org`، ‏`developer.mozilla.org`،
`developer.chrome.com` — أي نطاق آخر يُرفض بالكود قبل الطلب. البحث عبر SearXNG
المحلي فقط (`SEARXNG_BASE_URL`، في Actions حاوية محلية على localhost:8080).

## 4) المخططات (JSON Schema) وقاعدة «المحتوى بيانات»

- كل مخرجات وكيل تُتحقق من Schema قبل القبول؛ الرد غير الصالح = محاولة فاشلة.
- نتائج الأدوات تُغلَّف دائماً: `{"_meta": {...}, "data": {...}}` وتُمرَّر للنموذج
  برسالة `tool` — والتعليمات داخلها تُعامل نصاً (هذا البند مُختبَر في model_fit
  ببند `injection` وقاعدة القبول فيه الرفض التام).
- سجل JSONL لكل خطوة: `{ts, agent, role, action, tool, tokens, usd_floor,
  latency, ok, detail}` في مجلد نتائج التشغيل فقط.

## 5) ميزانية الخطوات والتكلفة (مفرضة بالكود)

| السقف | القيمة الافتراضية (models.json `caps`) | السلوك عند الاصطدام |
|---|---|---|
| خطوات لكل مقال (استدعاءات نموذج) | 40 | إيقاف نظيف + artifact جزئي |
| توكنات لكل مقال | 400,000 | إيقاف نظيف + artifact جزئي |
| دولار لكل مقال (أرضية أسعار الإدخال) | 1.00 | إيقاف نظيف + artifact جزئي |
| خطوات/توكنات/دولار لكل تشغيل (10 مقالات) | ×10 (التشغيل الكامل) | إيقاف نظيف |
| `RUN_COST_CAP_USD` للتشغيل الكامل | 5.00 | لا يبدأ التشغيل الكامل إن كان التقدير أعلى |

التكلفة تُحسب أرضيةً من أسعار الإدخال (`CLEANAPIS_CATALOG`) لأن أسعار الإخراج
غير مؤكدة من المالك — وهذا مُصرَّح به في كل تقرير. عدّاد التوكنات هو المقياس الأساسي.

## 6) حلقة التوليد لكل مقال (B)

1. المنسّق يبني خطة بحث (3 زوايا) ويفوّض بالتوازي.
2. الباحثون يعيدون مصادر مُتحقَّق منها (Schemas).
3. الكاتب (نموذج WORKER) يكتب المقال كاملاً بميزانية أقسام.
4. GATES — إن فشل باب: الكاتب يعيد توليد القسم الفاشل فقط (≤2).
5. CRITIC (نموذج مختلف) مراجعة استشارية واحدة → ملاحظات → الكاتب قد يصلح (ضمن سقف الخطوات).
6. GATES نهائية — الحاكم. النجاح → الناشر يكتب `candidate.md` + `report.json` كartifact.
   الفشل النهائي → artifact جزئي + سبب الإيقاف (لا نشر أبداً).

الذراع A (المقارنة): نفس منطق الخط المحسّن من فرع #450 منسوخاً داخل
`agents_v2/eval/pipeline_a.py` فقط (جلب SERP → استراتيجية → كتابة كاملة →
بوابات → إصلاح قسمي ≤2) — دون دمج #450 ودون أي تعديل على ملفاته.

## 7) الاختبارات

- لكل وكيل اختبارات وحدة بنموذج وهمي (mock provider يعيد ردوداً مُخططة):
  مسار سعيد، رد غير صالح Schema، حقن داخل نتيجة أداة، اصطدام سقف، توقف نظيف.
- بوابات `gates_local.py` تُختبَر بمقالات عينة نجاح/فشل (نفس بنود #450).
- كل الاختبارات بلا شبكة وبلا مفتاح — تعمل تحت `unittest discover` في CI.

## 8) ما هو خارج نطاق هذا التصميم عمداً

- أي تعديل على الخط الحالي أو daily-article أو workflows الموجودة (ممنوع بالتفويض).
- أي نشر تلقائي: نتيجة التجربة artifact فقط، والقرار النهائي بيد المالك وفق قاعدة
  القرار الثابتة (تبنّى B فقط إن اجتاز البوابات ≥ A وادعاءات غير مدعومة أقل ≥40%
  وكلفة ≤ 8× كلفة A).

## 11) تعديل قاعدة القرار وتصميم المحاولات العادلة (قرار المالك 2026-10-02)

بعد smoke #18/#19 اتضح أن التصميم الأحادي (محاولة واحدة لكل ذراع لكل موضوع)
يعاقب تقلّب النموذج لا جودة التصميم: مقال كامل 3176 كلمة خسر أمام باب واحد
(عدد الكلمات +76 عن السقف). عرضنا خيارين (تكرار المحاولة أو قبول "القريب")،
فحسم المالك بتغيير عادل للطرفين مع **عدم تخفيف أي بوابة وإعدام قبول أي مقال
"قريب" بأي بوابة فاشلة**:

### 11.1 التصميم الجديد (بند 2 من توجيه المالك)

- لكل ذراع (A وB) **الحد نفسه: 3 محاولات مستقلة لكل موضوع**، كل محاولة تبدأ
  من الصفر (لا حالة بين المحاولات، لا أفضل مقال من محاولات متعددة).
- الحلقة تتوقف عند **أول مقال يجتاز كل البوابات** (`gates_pass=True`) —
  البوابات كلها كما هي، فشل = فشل، ولا اختيار لأفضل مقال.
- يُسجَّل لكل ذراع ولكل موضوع ولكل محاولة: نجحت أم لا، رقم المحاولة،
  عدد الاستدعاءات والتوكنات والكلفة (استهلاك المحاولات الفاشلة يُحتسب
  لأنه استهلاك حقيقي عند المزوّد — إصلاح محاسبة الاستهلاك الجزئي في
  `agents.run_article` أدناه).

### 11.2 تعديل قاعدة القرار ولماذا

| الأصل (محاولة واحدة) | المعدّل (3 محاولات) | السبب |
|---|---|---|
| `gates(B) >= gates(A)` | `success_within_3_attempts(B) >= success_within_3_attempts(A)` | المقارنة الأحادية تقيس الحظ في محاولة واحدة؛ معدل النجاح خلال 3 محاولات يقيس الموثوقية بالمعيار نفسه للذراعين |
| `claims(B) <= 0.60*claims(A)` | `unsupported_claims(B) <= 0.60*unsupported_claims(A)` — على مقالات النجاح فقط | نفس عتبة 0.60 حرفياً، لكن مركّزة على الادعاءات **غير المدعومة** (أدق من العدد الكلي) وعلى المقال الفائز بالبوابات فعلاً؛ الموضوع الفاشل لا يُنتج مقالاً فيعاقَب عبر شرط النجاح لا عبر ادعاءات وهمية |
| `cost(B) <= 8*cost(A)` | `cost_per_successful_article(B) <= 8*cost_per_successful_article(A)` | الكلفة الكلية وحدها تكافئ الذراع الذي يفشل أرخص؛ «كلفة المقال الناجح» تقيس الإنتاجية الفعلية وتشمل كلفة المحاولات الفاشلة |

- عتبتا **0.60** و**8×** بقيادتهما الحرفية كما كتبهما المالك أولاً — التعديل
  في «على ماذا تُطبَّق» لا في «كم».
- **حارس المقدمة** محفوظ ومعزّز: تُقيَّم القاعدة فقط إذا أنتج كل ذراع مقالاً
  ناجحاً واحداً على الأقل؛ وإلا `adopt_B=null` (بعد أن أصدرت smoke
  36990401835 قرار adopt_B=true على بيانات صفرية).
- تعريفات المؤشرات الأربعة: نسبة النجاح من أول محاولة، نسبة النجاح خلال
  3 محاولات، متوسط المحاولات (الموضوع الفاشل يُحسب 3)، والتكلفة الكلية
  لكل مقال ناجح (كل محاولات الذراع ÷ عدد النجاحات).

### 11.3 إصلاح محاسبة التكلفة (بند 4 من توجيه المالك)

الخلل المكتشف: `run_article` كان يُرجع إحصاءات جزئية عند `BudgetExceeded`
فقط؛ أي خطأ آخر (رد غير قابل للتحليل مرتين، ProviderFatal، ...) كان يُفقد
كل استهلاك المحاولة (يُبلَّغ 0 استدعاءات / $0). الإصلاح: مسار استثناء عام
يملأ الإحصاءات من دفتر الاستخدام الحي قبل الإرجاع، و`journal.jsonl` يُكتب
**دائماً** حتى مع الفشل لتبقى استهلاكات كل استدعاء قابلة للتدقيق. مع
التصميم الجديد تُجمع كلفة المحاولات الفاشلة في `total_usd_floor` للذراع،
لذلك «كلفة المقال الناجح» رقم صادق.

المالك 2026-10-02). يُقسَّم سقف الذراع على محاولاته داخل الموضوع، والحلقة
